## 3. Target workflow and controlling contracts

### C1 — Preserve the idea before executing it

A topic, summary, question, personal account or existing text can be saved without model/provider qualification, trial enrollment, public references, score or image decision. Validate bounded input and storage integrity. Use an explicit provider-free writing-item representation; do not insert a malformed ordinary `prepared` job that old resume code would try to execute.

“Draft this” can save the brief and proceed automatically through applicable operations. “Save this idea” performs no model work. Source classification and technical IDs are managed by the application, with details available on demand. Do not introduce a chain of mandatory intake/approval forms.

### C2 — Intent governs preparation; support constrains assertions

Preserve Graham's supplied summary and intended point. Develop only enough direction to make the next useful version. Research addresses claims the intended piece needs; acquired papers must not replace the author's objective.

Handle personal accounts as attributed user input, opinion/inference proportionately, project achievements according to their actual records, and external assertions according to suitable evidence. User testimony is not independent proof of a measured achievement. Assistant status reports are not proof of installation, useful operation or business results.

Missing material is omitted, qualified, visibly marked or resolved by a focused question if indispensable. Do not invent then rely on a later review to repair it. An unsupported central assertion may yield a clearly limited outline or an information request; it must not be presented as established fact or a successful completed post.

Define supported input shapes coherently across `operational.py`, `operational_evidence.py`, `editorial_handoff.py`, `editorial_structure.py`, `contracts.py`, `api.py` and evidence validation. Current `validate_trial_evidence` supports local records but still requires a central fact/observation; current handoff/API assume matching factual anchors. Do not claim an installed opinion-only route from local-record support. Preserve strict historical trial shapes and compatibility explicitly.

Keep finite size/call/network bounds and untrusted-source instruction handling. Public HTTP protections remain intact; local personal records use an explicit record input, never private-address fetching disguised as public research. One or two short facts can remain a useful default, but must not be a universal permission to write.

### C3 — Separate author choice, automatic selection and experiment enrollment

A manually requested topic is an authoring request. Opportunity/novelty findings advise its development. Keep factual restrictions on what may be asserted. Autonomous topic-selection callers may rank or skip under their applicable policy.

Trial membership is explicit and linked to the particular experiment, not inferred from every create call, exact topic spelling or a new store. The existing `origin` field is descriptive context, not budget or execution authority. A caller cannot evade an original attempt restriction by relabeling it manual.

Preserve old trial counts, eligibility ambiguity, failures, sample partitions, policy IDs and admissions. Ordinary work may supply observations; it is not automatically an eligible trial or an unbiased comparison.

### C4 — Freeze execution snapshots and preserve original effects

When model-assisted development, drafting, rechecking or revision is requested, bind the current brief/text revisions, supporting records, model, voice, release/configuration and resource allowance to an immutable attempt before dispatch. Keep the writing item editable independently.

Retain same-ID/same-input zero-dispatch replay, changed-input conflicts and original provider/stage receipts. Proven non-dispatch is distinct from an uncertain dispatched effect.

Unfinished old-release attempts keep their binding. Use the original release or a specifically qualified compatibility/recovery path; do not silently rerun them with upgraded code.

### C5 — Save complete working text before downstream failure

Commit valid complete generated text as soon as it is available, before review/rewrite or optional visual work can prevent a normal authoring result. Preserve originals and later variants. A partial, malformed or absent provider response is not a successful draft.

Review failure or unavailable assessment attaches an honest status to saved text. Visual failure affects the visual task. Raw receipts remain available for recovery; users should not need to recover usable text from technical provenance JSON.

### C6 — Keep working text and qualification distinct

Show, comment on, manually edit and export actual working text regardless of whether it qualifies as `SelectedCandidate`. Do not populate that stricter type with unqualified text to gain editability.

Retain factual integrity, relevance, practical value and argument/voice findings. A machine assessment is evidence about the text, not Graham's acceptance. Parse valid essential findings independently of optional/advisory numerical dimensions; missing scores cannot erase valid essential findings. Missing/invalid essentials remain unavailable or failed, never silently passed.

Working-draft export includes the exact current text/version and true review/approval status. It does not claim qualified, approved, visual-ready or published status. Downstream consumers that require those states remain strict.

### C7 — Protect the current version against stale and late operations

Capture expected brief revision and expected parent text revision for relevant operations. Advance the current draft only if those expected versions still match; perform the check and update atomically in the existing store. A late result remains linked to its original inputs and retained as an alternative with an explicit conflict.

A human edit B made while a revision from A runs stays current when A's model result arrives. Both results survive. Apply equivalent stale-input protection to UI saves and reviews. A review attaches only to its reviewed bytes and cannot certify a newer brief/text version. Resolving a conflict does not automatically generate again.

### C8 — Continue writing separately from recovering execution

Support adding missing information, deliberately revising the current draft, saving a manual edit and checking the exact edited text. Preserve the prior attempt's terminal outcome.

Recording feedback, reading, reopening, previewing and exporting invoke no model. A requested recheck assesses the current bytes without silently rewriting them. A requested model revision preserves the original and creates a properly admitted linked attempt. Invalidate affected reviews, visual bindings and approval claims after a change while retaining their historical evidence.

Use actual supplied feedback. Numerical labels, editing minutes, keep/light classifications and reusable voice-example approval are optional observations until actually supplied. Explicit example approval and separate activation remain required for global voice learning; max-three example injection and factual/style separation remain with the existing contract.

### C9 — Separate writing lifetime from execution deadlines

A writing item can be revisited after a human pause. Future deliberate actions receive the applicable finite execution window and legitimate resource admission. Preserve cumulative actual usage and any broader still-applicable cap; opening/relabeling a record never renews an allowance.

This is prospective. Historical expired admissions stay expired, consumed budgets stay consumed and UNKNOWN attempts retain their original identities/limits. Long human review must not become a requirement to finish the entire piece inside the original short machine window.

Retain all attempted outcomes, blocked starts, failures and unavailable assessments in operational observations. Keep the defined paired-editorial denominator separate from this complete operational experience; do not rewrite historical trial denominators.

Existing `codex_trial.py` helpers are reusable experiment components; the current quick-start labels their CLI compatibility/development surfaces. They are not automatically qualified shortcuts around ordinary application admission.

### C12 — Simplify from observed value
