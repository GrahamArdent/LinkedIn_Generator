# Preserved single guarded rewrites

Neither qualified for selection. Original first drafts remain the blinded comparison.

## security

An office key lets you open the door. It doesn’t give you permission to take the equipment home.

A familiar account can create the same confusion: access gets mistaken for approval.

Cloudflare reports that account access details stolen in the October 2023 Okta compromise were mistakenly considered unused and left unchanged. Attackers later used them to access its Atlassian work systems.

The lock still accepted the key.

A separate CERT-In report describes attackers using stolen access details to send fund-transfer requests directly between computers, from victims’ own recognized company systems. They bypassed application checks and transferred money into accounts used to receive stolen funds.

Even the familiar company systems were part of the route in.

These different incidents illustrate the gap between accepted access and permitted action. They don’t prove that a particular safeguard would have prevented either incident. The office key is an analogy for access, not a description of what was stolen.

For me, the practical test is whether approval is required for the action to happen, or merely expected along the way.

Take one sensitive request you’re responsible for approving. Identify the approved record, what it permits, the intended recipient and any amount limit.

Then ask the person responsible for the process to show what happens when that evidence is missing or doesn’t match the request. Does the action stop before it happens? Can another route skip the check?

A record of approval is useful. Evidence that the action cannot proceed without that approval answers the harder question.

Recognizing where a request appears to come from is only part of the decision. You still need to establish what this particular request is allowed to do.

## ai

The draft arrives in seconds. Approval still takes work.

If you approve work, the useful measure is how long it takes to reach something you can use.

A Stanford-published study of 5,172 customer-support agents reported a 15% average increase in issues resolved per hour with AI assistance. Resolved issues: a stronger measure than output produced.

In METR’s randomized study, 16 experienced open-source developers completing 246 tasks took 19% longer with early-2025 AI tools.

Different workers, tasks and tools, not a matched comparison. The support finding concerns one deployment; METR’s result is historical, not an estimate of today’s performance. Neither establishes checking as the cause of the slowdown.

My takeaway: before calling a faster draft a time saving, count the work needed to approve it. The approver’s time belongs in the total too.

For one repeated task, I’d compare time to usable completion with and without AI, using the same approval standard. Count time spent giving instructions, checking and correcting, whoever does it.

That’s a test I’m proposing, not a finding from these studies. It would help distinguish work removed from work passed to the next person.

I’d judge the saving at approval. That’s where a quick draft has to become usable work.
